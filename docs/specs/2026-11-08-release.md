# Releaseflöde: Release Please och TestFlight

Ärende: #27. Status: godkänd av Jesper 2026-11-08.

## Mål

En release görs genom att Jesper mergar en PR på GitHub, även från mobilen. Det som sker sedan sker i GitHub Actions: version, changelog, tagg, GitHub Release, bygge, signering och uppladdning till TestFlight. Ingen dator behövs. Varje uppladdning godkänns av Jesper, och App Store-inskickning görs för hand i App Store Connect.

## Flödet

1. Commits når `main` genom squash-mergade PR:er med titlar enligt Conventional Commits.
2. Workflowen **Release** körs vid varje push till `main`. Release Please (`googleapis/release-please-action`, versionstyp `simple`) håller en öppen release-PR med nästa version i `version.txt`, `CHANGELOG.md` och appens versionsfil.
3. Jesper mergar release-PR:en. Release Please skapar taggen `vX.Y.Z` och en GitHub Release med changelogens avsnitt som text.
4. I samma körning, bara när en release skapades, startar jobbet **TestFlight**. Jobbet kör i miljön `testflight`, som har Jesper som obligatorisk granskare. GitHub väntar alltså på hans godkännande innan något byggs.
5. Efter godkännandet bygger, arkiverar och signerar jobbet appen och laddar upp den till App Store Connect. Bygget dyker upp i TestFlight efter Apples bearbetning.
6. Inskickning till App Store gör Jesper själv i App Store Connect.

TestFlight-jobbet ligger i samma workflow som Release Please. En tagg som skapas med `GITHUB_TOKEN` startar inga andra workflows, och på det här sättet behövs ingen personlig token. Workflowen kan också startas för hand (`workflow_dispatch`) med en befintlig tagg, om en uppladdning behöver göras om.

## Versioner

- Versionen följer Conventional Commits: `feat:` höjer minor, `fix:` höjer patch och `!` eller `BREAKING CHANGE:` höjer major. `docs:`, `test:`, `ci:`, `chore:`, `refactor:` och `build:` ger ingen release.
- Första releasen blir **1.0.0** (`release-as` i konfigurationen för den första releasen, och raden tas bort efteråt).
- Appens version (`MARKETING_VERSION`) ligger i en egen fil, `iOS/Config/Version.xcconfig`, med en markering som Release Please uppdaterar. `iOS/project.yml` pekar på filen. Därför ändras aldrig den committade `Sophamtning.xcodeproj` vid en release. Båda `Info.plist` läser `$(MARKETING_VERSION)` och `$(CURRENT_PROJECT_VERSION)` i stället för de fasta `1.0` och `1`.
- Byggnumret (`CURRENT_PROJECT_VERSION`) räknas fram i jobbet: `github.run_number` × 100 + `github.run_attempt`. Det ökar alltid, också när en körning görs om. I repot står byggnumret som `1` och används bara lokalt.
- Version och changelog ändras aldrig för hand.

## Signering och hemligheter

- Bygget signeras automatiskt (`-allowProvisioningUpdates`) med en App Store Connect API-nyckel. Xcode hämtar eller skapar certifikat och profiler själv. Inga certifikat eller profiler ligger i repot.
- Jesper skapar nyckeln i App Store Connect och lägger in tre hemligheter i miljön `testflight`, inte i repot som helhet:
  - `ASC_KEY_ID`
  - `ASC_ISSUER_ID`
  - `ASC_KEY_P8`: nyckelfilens innehåll, base64-kodat
- Nyckeln skrivs till en fil i `$RUNNER_TEMP` och tas bort i ett steg som alltid körs. Värdena skrivs aldrig ut i loggen, och inget steg kör `set -x`.
- Nyckelns roll ska vara den lägsta som räcker för molnhanterad signering och uppladdning. Det kontrolleras i planens första steg mot Apples dokumentation.

## Bygget

- `runs-on: macos-26` och Xcode 26.6, samma som i `ios.yml`.
- Paketets tester körs först, som i `ios.yml`. Fallerar de laddas inget upp.
- `xcodebuild archive` med konfigurationen Release, och sedan `xcodebuild -exportArchive` med en `ExportOptions.plist` i repot: metoden `app-store-connect` och `destination` `upload`. Exporten laddar alltså upp direkt. Inga verktyg utanför Xcode, till exempel fastlane.
- Arkivet (`.xcarchive`, med dSYM) sparas som artefakt i 30 dagar, så att kraschrapporter kan symboliseras.

## Säkerhet

- Alla actions är fastlåsta på en commit-SHA, som i `ios.yml`.
- `permissions` är minsta möjliga: `contents: write` och `pull-requests: write` för Release Please, och `contents: read` för TestFlight-jobbet.
- Hemligheterna finns bara i miljön `testflight`, som kräver Jespers godkännande. En PR från en fork kommer aldrig åt dem, eftersom workflowen bara körs på `main` och för hand.

## Det här ingår inte

- Inskickning till App Store och texter till App Store-sidan (finns i `2026-11-06-app-store.md`).
- Text i "Vad ska testas" i TestFlight. Den kan läggas in för hand. Att skicka den automatiskt kan bli ett senare ärende.
- Android.

## Följdändringar

- `CLAUDE.md`: raden om `MARKETING_VERSION` i `iOS/project.yml` ändras till `iOS/Config/Version.xcconfig`. Avsnittet Releaser beskriver flödet som på plats.
- `CONTRIBUTING.md` och `README.md` får en kort rad om hur en release görs, om de beskriver det i dag.

## Klart när

- En merge till `main` med en `feat:`- eller `fix:`-commit ger en release-PR, eller uppdaterar den som redan finns.
- En merge av release-PR:en ger taggen, en GitHub Release och ett TestFlight-jobb som väntar på godkännande.
- Efter godkännandet finns bygget i App Store Connect med rätt version och ett byggnummer som ökar.
- Inget hemligt värde syns i loggen.
